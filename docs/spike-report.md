# Spike 报告：激活扩散引擎验证（v1 初步搭）

> 日期：2026-08-21
> 目的：验证设计核心命题——"查询锚定 PPR + 激活扩散 → 节点簇"在真实库上能否产生"我没想到但确实相关"的节点；重测 λ/θ/hops（决策 #5）；为 v1 定稿打分机制。
> 载体：`seren` CLI（Go 单二进制，零依赖，in-memory），数据 = 一个中文小说 Wiki 库快照（作者个人库，150 节点 / 1141 去重无向边）
> 隐私：本报告中的查询示例来自作者个人库，**人物/线索/设定名称已脱敏为语义占位**（如"主角/幕后推手/关键线索"）。

## 一、结论先行

1. **核心机制成立**：查询锚定 PPR + 激活扩散在真实 wiki 图上稳定产出"一片相关节点"，1-hop 簇质量高（主角 → 关联人物/线索/设定全部命中）。
2. **serendipity 不是相关度的副产品**：纯相关度排序结构上出不了深跳惊喜节点（枢纽-辐条图里 1-hop 邻居洪泛）。**必须显式加"跳数配额混合"机制**——实测后 2-hop 惊喜节点（幕后推手/关键线索/关键设定）质量优秀。
3. **λ/θ/hops 重测结论（决策 #5 交付）**：λ=0.5/θ=0.2 在真实密度下只露出 1-hop；λ=0.7/θ=0.1 时 2-hop(0.49)/3-hop(0.343) 可达。**建议 v1 默认 λ=0.6~0.7, θ=0.1, hops=3**；但可及性只是前提，可见性靠跳数配额。

## 四、参数重测（决策 #5 交付）

| 参数 | mneme 初值 | spike 实测 | 建议 v1 |
|---|---|---|---|
| λ | 0.5 | 0.5 时 2-hop=0.25 被 1-hop 完全压制 | **0.6~0.7** |
| θ | 0.2 | 0.2 时 3-hop=0.125 被剪 | **0.1** |
| maxHops | 3 | 3 跳内可及性足够（图太密，更深无意义） | **3**（不变） |
| PPR teleport | 0.15 | 稳定收敛，无异常 | 0.15（不变） |
| 新增 | — | **跳数配额 1:2:3-hop = 0.5/0.3/0.2**（serendipity 机制） | 纳入 v1 默认 |

> 关键洞察：**λ/θ 决定"可及性"，配额决定"可见性"**——两者解耦后，λ/θ 的敏感度大幅下降，配额的形状才是 serendipity 的主旋钮。

## 六、架构补充：VaultProfile（解析规则抽离）

用户提出的关键约束："解析方案不能四海皆准，得把解析语法抽离出来"。落地：

- **通用语法**（`[[...]]` / frontmatter / H1）代码固定——Obsidian 标准，人人相同。
- **VaultProfile（库画像）**：title/别名/标签键、排除目录、类型推断规则全部 YAML 化，`<vault>/.serendipity/profile.yaml` 跟库走；内置 `default-obsidian` + 一个示例画像（`example-wiki`，演示"按库覆盖"）。
- **`seren profile-detect <vault>`**：扫描新库 → 自动产出画像骨架（键普查/目录/前缀/结构类型猜测），人工微调即用——**换库不再改 Go 代码**。
- 实测：示例画像下，章节/大纲/报告/index/种子全部从簇输出排除，2-hop 惊喜保留。

## 附：构建与运行

```powershell
$env:GOCACHE="<workspace>\scratch\.gocache"; $env:GOPATH="<workspace>\scratch\.gopath"
go build -o seren.exe ./cmd/seren
.\seren.exe index <vault>                          # 图统计
.\seren.exe roam <vault> <query>                   # 漫游（.db 自动识别虎鲸）
.\seren.exe serve <vault> --port 8080              # Web UI
.\seren.exe index <vault> --persist                # 持久化
.\seren.exe roam <vault> <query> --db <store>      # 从存储读图
```
