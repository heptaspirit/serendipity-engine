# Serendipity Engine · 奇遇记引擎（修订版）
## 图谱漫游：让双链真正跑起来（Graph Roaming: Making Bidirectional Links Come Alive）

> 日期：2026-08-21
> 修订：v2（2026-08-21，整合 `docs/DESIGN_REVIEW.md` 中 13 条评审决策）
> 性质：独立设计研究（本地 CLI + Web 工具构想，不绑死任何笔记软件）。与 dsh-mneme 图谱增强同哲学、不同领域——mneme 管 agent 记忆，本文管**人的笔记导航**。
> 起因：① Obsidian 图谱是死地图——双链如果不主动点，就永远没有下文；② 研究 dsh-mneme 图谱增强（核心命题「结构 × 激活」）时意识到：同一套激活引擎，换个载体、换个人当消费者，就是"让 wiki 真正跑起来"。
> 定位：**查询驱动的图谱漫游（pull）**——用户查询某个点（笔记/词/标签），自动得到一批经过筛选、排序、可解释的相关节点。这是渐进阅读（push，调度）之外的另一种东西：**在笔记中漫游**。

## 〇、核心命题

> **图的价值 = 结构 × 激活。任何一个为零，图就是死的。**

（继承自 mneme 图谱哲学）笔记软件有结构（双链）、没有激活（运行时信号），所以它的图谱是静态装饰。**本文要做的事：给笔记双链装上激活引擎，让链接网络对查询作出响应。**

wiki 的原始承诺——知识通过链接自组织、词条之间互相引路——在个人笔记里从未真正兑现：双链是"等着被点击"的地图，不是"会响应"的网络。本文的方案就是兑现这个承诺：**你问一个点，它给你一片。**

## 一、概念定位：拉（pull），不是推（push）

先钉死概念，避免与渐进阅读（progressive reading）混淆——这是本设计最容易被人误读的地方。

| 维度 | 渐进阅读（push） | 图谱漫游（pull，本文） |
|---|---|---|
| 驱动 | 时间 / 进度调度——什么时候该读 | 查询 / 意图——问什么给什么 |
| 输出 | 下一步该读的 1-3 篇 | **一批筛选后的相关节点**（一片区域） |
| 锚点 | 最近漫游的 / 当前进度 | 用户查询点（词、标签、任一笔记） |
| 目的 | 管理学习流程 | 知识导航与探索（serendipity） |
| 用户角色 | 被动接收推荐 | 主动发起，然后自由选择路径 |

渐进阅读（SuperMemo 系）其实是两个东西的混合物：

| 组件 | 本质 | 驱动方式 |
|---|---|---|
| 切块 + 间隔重复（FSRS） | 复习调度 | 时间驱动（遗忘曲线） |
| 增量披露 | 每次只暴露"下一步" | 人工编排（文本顺序） |

本文做的是**增量披露的图谱版本**：让**双链拓扑**决定导航/披露顺序，时间只作修正（heat）。它不碰复习调度——长文该不该读的标准是难度/进度/重要性/紧迫性/兴趣，不是"记忆程度"（该判断已被 Roaming Mode 项目的外部实践印证，见 §五）。

## 二、现状诊断：双链为什么是死的

| 工具 | 有什么 | 缺什么 |
|---|---|---|
| Obsidian Local Graph | 显示邻居节点 | 不筛选、不排序、不解释 |
| Obsidian Backlinks | 直接入链列表 | 只到 1-hop、无激活、无优先 |
| Roam / Logseq | linked references | 无拓扑驱动的推荐/漫游 |

导航需要四个能力，现有工具全缺：

1. **筛选**：激活后的相关簇（多跳 + 剪枝），不是平铺的邻居
2. **排序**：每个节点有分数，解释为什么它在前面
3. **可解释**：这条节点经哪条双链连过来（激活路径）
4. **可干预**：认可 / 忽略 → 反馈回边权

这四点不是锦上添花，是"导航"和"看地图"的分界线。Local Graph 是地图——所有路都画给你，但不知道哪条值得走；图谱漫游是"活的向导"——告诉你此刻从 A 出发，哪些路值得走。

## 三、核心机制

### 3.1 查询 → 激活扩散 → 节点簇

```
用户查询点（笔记 / 词 / 标签）
  → 锚定（精确名 / 标签 / 全文命中，起点是集合非单点）
  → 双链激活扩散（λ 衰减 + θ 剪枝，多跳；关联边对称，传递边沿"来源→拓展"方向传播）
  → 四维打分融合
  → 输出 top-10~20 节点簇（带分数 + 激活路径）
  → 用户消费（读 / 跳过 / 深入）→ touch → 边权更新
  → 下次查询更强（正循环，衰减约束）
```

### 3.2 四维打分

| 维度 | 信号 | 来源 | 语义 |
|---|---|---|---|
| 结构分 | **查询锚定的 PPR**（Personalized PageRank，以查询点为种子） | 图拓扑 | 在以当前查询为背景时，这是枢纽还是跨主题跳板 |
| 激活分 | 从查询点出发的扩散值 | 激活扩散（λ 衰减 + θ 剪枝） | 离我此刻的思维有多近 |
| 时效分 | heat / recency | 访问记录 + 分层衰减 | 现在还重不重要 |
| 依赖分 | 引用方向推断 | 边语义（§3.3：冷统计 + 热行为） | 我该先读它吗 |

**〔修订 #1〕结构分从全局 PageRank 改为查询锚定的 PPR**——全局中心性会让同一批"枢纽"节点霸占每一次查询的头部、扼杀 serendipity 与查询特异性；PPR 以查询点为种子，结构分随查询而变。（HippoRAG 同款思路，见参考 3。）

融合公式：`分数 = α·结构 + β·激活 + γ·时效 + δ·依赖`。

**〔修订 #4〕每维先归一化再融合**——四维量纲天差地别（PPR 概率 ~1e-5、激活分指数衰减、依赖分 D∈[−1,+1]、heat 任意尺度），不做归一化则 α/β/γ/δ 的取值与实际占比完全脱钩。v1 统一采用 min-max 或 rank 分位归一后再线性融合。

**〔修订 #3〕δ 默认 0**——依赖分回答的是"该先读它吗"（阅读顺序），与"探索/找惊喜"（导航）是两个目标，混进一个排名会互相打架。v1 默认场景（导航/探索）中 δ=0；依赖分单独做成 §3.4 的"路径排序"输出，不进 serendipity 排名。

**〔修订 #13〕四维权重 v1 只有一组全局默认**，α/β/γ/δ 按场景配置（纯导航、复习提醒、主题切换）是 v2 的可选项，不做进 v1。γ（时效）默认 0——v1 不引入 heat，理由见 §7.2；如需锚定消歧 / 漂移检测再启用。

### 3.3 边语义：关联 vs 传递（群友反馈升级）

双链至少有两种语义，直接决定导航方向：

| | 关联（Association） | 传递（Transmission） |
|---|---|---|
| 本质 | 对称、静态——"A 让我想起 B" | 非对称、有方向——"A 是 B 的前置 / 读完 A 再读 B" |
| 图论特征 | 互链、双向、结构等价 | 单向、入度/出度不对称、路径顺序一致 |
| 导航含义 | 相关的兄弟 | 来源（该先读）/ 拓展（继续读） |
| 对应打分 | 结构分（无向） | 依赖分（有向） |

**关键约束：用户自己也说不清链接语义 → 不能要求标注，用推断替代。** 推断分冷热两个信号源。

**〔修订 #2〕v1 默认所有边当无向关联，单向链接不再升级为"传递"。** Obsidian 里单向链接极其常见且绝大多数只是"随手链一下"（"这让我想起那个"），不是"读完 A 再读 B"——按单向→传递推断会系统性误判，把导航掰偏、污染依赖分。

**冷启动（写入即确定，纯统计零 LLM）：**

| 信号 | 指向 | 理由 |
|---|---|---|
| 互链（A↔B 双向） | 关联 | 互相引用 = 对称兴趣（v1 默认即关联，此项确认而非升级） |
| 全库路径顺序一致性 | 传递（唯一升级信号） | 大量路径按 A→B→C 顺序出现 → 传递链 |
| ~~单向 A→B~~ | ~~传递~~ | **〔修订 #2〕已删除**——单向链接噪声太大，不构成方向证据 |
| ~~入度 / 出度比~~ | ~~传递方向~~ | **〔修订 #2〕已降级**——引用多 ≠ 前置，可能只是热门概念，留作 v2 探索项 |

**热启动（行为反馈，微妙点集中在此）：**

热启动的本质是"用户实际怎么读"比"链接怎么画"更诚实。三个微妙点必须处理：

1. **信号源分层**：v1 只用**漫游工具内部行为**（点节点簇里的哪条、停留多久、是否展开）——零依赖、可控，但样本只在漫游时产生；v2 接 adapter 的**笔记软件访问记录**（虎鲸块访问 / Obsidian 打开记录）——样本充足但依赖适配器。两级都可选，不阻塞核心。
2. **有效转移定义**：不是"打开就算读"。只记**有效转移**——目标节点停留 ≥ 5s 且无快速回跳（3s 内回到原节点不算）。短停留点击多为随机探索，会污染方向推断。
3. **防自指污染**：推荐列表本身有顺序，用户点列表前几个会让"点击顺序"被推荐顺序伪造。对策：**只用停留时长和展开动作做信号**（时长不可被顺序伪造），点击顺序本身不作为信号。

**推断统计量**：每条边存两个有向计数 (A→B, B→A)，EWMA 平滑（近期行为权重高）。方向分 `D = (N→ − N←)/(N→ + N←) ∈ [−1, +1]`；**置信度门槛**：总转移 ≥ 3 次才更新，否则维持冷启动先验；冷热融合 `传递度 = w_cold·cold + w_behavior·behavior`，行为权重随积累从 0 上升。跨会话积累（建议 2-3 个会话后才影响排序）防单次探索噪声。

**扩散分化**：关联边**无向对称扩散**；传递边**有向扩散**——沿"来源→拓展"方向传播更快更远，逆方向衰减。激活扩散因此从无向升级为方向性传播（§3.1）。

**参数初值**：停留阈值 5s / 回跳窗口 3s / 置信门槛 3 次 / EWMA 半衰期 7 天。

### 3.4 输出形态：给区域，不给单点

导航的目的是让用户看到**这片区域的形状**，然后自己选路径——所以输出是一批（10-20 条），每条带分数和激活路径说明（"这条经 X 双链连过来"）。

**〔修订 #3〕依赖分独立为"路径排序"输出**：当用户点选某条节点/边时，额外给出"建议先读 X（前置）→ 再读它"的依赖顺序提示。这属于阅读顺序的辅助信息，不进节点簇的 serendipity 排名。

**〔实测新增〕跳数配额混合（serendipity 机制，spike F1）**：纯相关度排序在枢纽-辐条图上会让 1-hop 邻居洪泛、2-hop+ 惊喜节点永不露面。v1 排序在归一化融合后**按跳数配额混合取 top-N**（默认 1:2:3-hop = 0.5/0.3/0.2）——这是 serendipity 的主旋钮；λ/θ 只决定可及性（见 `docs/spike-report.md` §四）。实测 2-hop 惊喜质量高：主角 → 幕后推手、关键线索、关键设定（示例库内容已脱敏）。

**〔实测新增〕目录枢纽与种子排除（spike F2/F3）**：度 ≥ 半数节点的目录页（如 index，连 129/150 节点）从结果中排除——它是"地图"，不是"目的地"；锚点种子（0-hop）是查询本身，也从结果中排除。

与阅读调度的输出形态对比（互补，不冲突）：

| 场景 | 触发 | 输出形态 |
|---|---|---|
| 图谱漫游（导航） | 用户查询一个点 | 一批节点簇（10-20 条）+ 分数 + 路径 |
| 阅读调度（如后续做） | 读完当前笔记 | 1-3 条 + 推荐理由 |

### 3.5 反馈闭环

- **读 = 隐式认可** → 边权 ↑（被读过的路径加粗，PDP"每用一次路径加粗一点"）
- **跳过多次** → 异常介入三选一：暂时不想看 / 内容无关 / 链接标错了
- **人工旋钮**（用户显式优先级，见 §6.5）防隐式信号的正反馈循环

## 四、与 mneme 的关系：同引擎，双界面

这是本设计最重要的一个洞察：**笔记漫游与 mneme 图谱增强是同一个激活引擎的两个实例化**——数据源和消费者不同，机制完全同构。

| 环节 | mneme（agent 侧） | 图谱漫游（人侧） |
|---|---|---|
| 查询 | 会话 query | 用户查询点 |
| 锚定 | matchEntities（精确名 / Tag / 向量三层） | 节点名 / 标签 / 全文命中 |
| 扩散 | entity_relations 多跳 | 双链 links_to 多跳 |
| 融合 | 语义分 × tagBoost × (1+激活) | 结构 × 激活 × 时效 × 依赖 |
| 输出 | 注入 system prompt 给 LLM | 可视化节点簇给用户 |

**哲学借用清单**（直接搬，坑已在 mneme 研究里踩过）：

| 机制 | mneme 出处 | 本文用法 |
|---|---|---|
| 结构 × 激活 核心命题 | 图谱哲学 §〇 | 总纲不变 |
| 激活扩散参数（λ=0.5 / θ=0.2 / maxHops=3） | 图谱哲学 §5.5 | **〔修订 #5〕初值继承，待 spike 重测** |
| 边权按来源分级 + 衰减继承 type | 图谱哲学 §5.10 | 手动链接高权 / 自动边低权起步 |
| 白盒原则（可解释 / 可干预 / 可审计） | 图谱哲学 §1.3 | 路径可显示、认可/删除留痕 |
| 反馈闭环（touch → 路径加粗） | 图谱哲学 §5.6 | 原样继承 |
| 人工确认三选一（被动 + 异常介入） | 图谱哲学 §5.10 | 原样继承 |

**需要改的**（两处本质差异）：

1. **冷启动相反**：mneme 图谱要等 touch 数据积累（激活驱动建图）；笔记双链**天然带权冷启动**——引用关系是写入时确定的，结构分和依赖分在第一天就存在，无需建图成本。
2. **消费者不同**：人不是 LLM。输出形态从"注入文本"变成"可视化面板"；时效维度在个人知识库规模下权重可能远小于 mneme（值得单独实测）。

**边界声明**：独立项目，不属于 mneme 范围。mneme 管 agent 记忆，本文管人的笔记导航。两者的共同点是哲学与机制骨架，不是代码。

**双消费者设计（用户拍板方向）**：筛选引擎的产出 = 一组 `(节点, 分数, 激活路径)`。同一份产出开两个输出通道——

- **通道 A（人）**：渲染为导航面板（节点簇图 / 排序列表 + 分数 + 路径）
- **通道 B（AI）**：序列化为注入块（如 `[相关节点] 查询点 X 附近：…`），供笔记软件内的 AI 助手消费——**既然筛选器能对人起作用，同样的结果对 AI 也一样可用**，零额外成本。

## 五、对标：Roaming Mode Incremental Reading（思源笔记插件）

> 仓库：https://github.com/ebAobS/roaming-mode-incremental-reading（活跃维护，2026-06 仍有提交，v4.2.x）

它是现存最接近本构想的项目，值得作为 baseline 和"不该做什么"的对照。

**它是什么**：思源笔记插件，只做渐进阅读流程的第一步——"稍后阅读"的**文档推荐**。核心机制：TF-IDF 余弦相似度（锚点 = 最近漫游 N 篇 + 高频漫游 M 篇）+ 人工指标权重（难度 / 进度 / 重要性 / 紧迫性 / 兴趣）+ 轮盘赌随机混合，侧边栏排序展示。明确反对文章级遗忘曲线。

**对比**：

| 维度 | Roaming Mode | 图谱漫游（本文） |
|---|---|---|
| 关系信号 | TF-IDF 文本相似度（内容"像不像"） | 双链激活扩散（关系"相不相关"） |
| 锚点 | 最近漫游 + 高频漫游（时间聚合） | 用户查询点（上下文单点） |
| 打分 | 人工指标权重 + 余弦相似度 | 结构 × 激活 × 时效 × 依赖（机器演化） |
| 披露节奏 | 侧边栏列表 + 轮盘赌随机 | 节点簇 + 分数 + 激活路径 |
| 图谱 / 双链 | 完全缺席 | 核心载体 |
| 兴趣漂移 | 间接（锚点隐含） | 显式 heat + 可选漂移检测 |

**它验证了什么**：① "渐进阅读第一步值得做成推荐器"需求真实存在；② 文章级遗忘曲线被外部实践否定——与本文"拓扑驱动 + 时间修正"路线同构。

**它缺什么（= 本文差异化）**：TF-IDF 本质是"没 embedding 时代的语义相似"，只找**像的**，找不到**相关的**（embedding 桥不动的长尾关系：跨项目工具偏好、项目换方案的失效等）。没有依赖顺序、没有披露节奏、没有主题徘徊/漂移检测。

**该偷什么**：**用户显式优先级旋钮**——人工定义指标 + 权重百分比 + 散点图拖拽调整。纯隐式信号（touch/heat）有"越推越读、越读越推"的正反馈风险，人工旋钮把"人的意图"放回回路，是 mneme 5.10"确认 = 强反馈信号"的用户侧变体。

## 六、设计细节

### 6.1 参数继承（mneme 已验证区间 → 初值待重测）

| 配置 | 默认 | 说明 |
|---|---|---|
| 衰减因子 λ | **0.6~0.7** | 每跳衰减；spike 实测 0.5 时 2-hop(0.25) 被 1-hop 完全压制（docs/spike-report.md §四） |
| 激活阈值 θ | **0.1** | 低于 θ 剪枝；spike 实测 0.2 会剪掉 3-hop(0.125) |
| 最大跳数 maxHops | 3 | 深跳是弱关联的征兆；spike 实测 3 跳可及性足够 |
| 输出规模 | 10-20 条 | 给"区域形状"，不是单点 |
| **跳数配额** | **1:2:3-hop = 0.5 / 0.3 / 0.2** | **〔实测新增〕serendipity 机制，见 §3.4** |
| 时效权重 γ | **0（默认关闭）** | v1 不引入 heat，见 §7.2 |
| 依赖权重 δ | **0（默认关闭）** | **〔修订 #3〕v1 依赖分独立为路径排序，不进导航排名** |
| 边初始权重 | 手动 1.0 / 自动 0.3-0.4 | 按来源分级，靠使用塑造 |

**〔修订 #5〕λ / θ / maxHops 是"初值"不是"已验证区间"**——mneme 的图是 agent entity_relations，笔记双链图的密度、度分布、查询模式完全不同。**spike 已重测（2026-08-21）：λ=0.6~0.7 / θ=0.1 / hops=3 / PPR teleport=0.15，详见 `docs/spike-report.md` §四。** 关键洞察：λ/θ 决定"可及性"，跳数配额决定"可见性"——两者解耦后 λ/θ 敏感度大幅下降。

### 6.2 冷启动：双链天然带权

与 mneme 相反，笔记双链**写入即确定**：结构分（PPR）和依赖分（引用方向）第一天就存在，无需实体抽取、无需等待 touch 积累。

**〔修订 #9〕冷启动的定位需收窄**——结构/依赖第一天确实存在，但"好推荐"仍靠行为数据演化；而 v1 行为样本极稀（单用户、查询驱动低频、每条边置信门槛 3 次、跨 2-3 会话生效），热启动长期休眠。因此 **v1 的价值定位 = 结构驱动的导航**（PPR + 双链拓扑），"越用越准"的行为演化是 v2 增益，不作为 v1 卖点。

### 6.3 反馈信号与正反馈风险

- "读"怎么定义：停留时长是弱信号（可能挂机），显式"标记已消化"是强信号但打断流
- 无可靠反馈 → 权重退化为"越点越多"的正反馈循环
- 对策：被动路径（读 = 隐式认可）+ 异常介入（跳过多次才打扰用户）+ 人工旋钮
- **touch 升级为有向转移**（§3.3 热启动行为源）：touch 不仅 bump 边权，还记录"从哪来"——用户从节点簇的 A 跳到 B，记一笔有效转移 A→B（有效定义见 §3.3）。阅读序列成为边语义的强信号："被读的顺序"暴露真实的传递方向，比链接画法更诚实。

### 6.4 白盒原则

- 每个推荐节点**必须可解释**：显示激活路径（"经 X 双链，1-hop"）
- 用户可干预：忽略 / 删除链接 / 调优先级，全部走审计留痕
- 自动产生的"推荐理由"是防噪声的第一道闸——用户需要知道它为何在此

### 6.5 人工旋钮（从 Roaming 偷的设计）

一维人工可调项（如"兴趣"或"难度"）作为四维打分的修正系数：机器管结构 / 激活 / 时效，人管意图。可拖拽调整，反馈立即影响后续漫游。

### 6.6 AI 双通道（见 §四）

同一份 `(节点, 分数, 路径)` 产出，人看面板、AI 读注入块。通道 B 让"筛选器暴露给 AI"成为零额外成本的设计决策，而不是事后补丁。

### 6.7 建库 = 解析：AI 的定位是补图

"全库扫"在这里有两种含义，成本差两个量级：

| | 含义 A：LLM 实体抽取（mneme 式） | 含义 B：双链解析（笔记式） |
|---|---|---|
| 做什么 | AI 读全文抽实体 / 关系 | 文本解析读 `[[链接]]` |
| 成本 | 重（每篇一次 LLM） | 轻（纯文本，几千篇几秒） |
| 效果 | 不一定好（关系是**猜的**） | 100% 准（关系是**用户写的**） |
| 是否必要 | 冗余——双链已显式存在 | 必须，且就是"建库"的全部 |

**建库 = 解析 = 同步**：双链场景没有"建图"这一步，只有"读图"。每次启动全量重扫（秒级），文件变更增量重扫相关文件。mneme 要造图（隐式关系要抽），笔记图是白送的（显式关系读就行）——这是本构想比 mneme 图谱轻一个量级的根本原因。

**AI 预算从「造图」移到「补图」**——图白送之后，AI 全库扫的合理用途是补用户链接习惯留下的洞：

1. **补链**：发现"该有链接但没有"的潜在关联（孤儿笔记、语义相近未互链）——唯一真正高价值的 AI 用途，因为人会画漏
2. **推荐理由**：为什么推这条（按需、轻量）
3. **语义锚定**：自然语言 query 时（见 §6.8 语义层）

补链是**建议不是写入**（白盒原则，用户确认后才生效）。成本形态从"建库的一次性大额"变成"补图的按需小额"。

**成本结构镜像**：mneme 为"建图"省钱（激活驱动、拒绝全量），笔记漫游为"补图"花钱（按需增强）——钱的去向相反，因为图的来源相反。

### 6.8 技术栈与产品形态：核心服务 + 三入口

**产品形态（用户拍板）**：本地 CLI + 人工可用的 Web 应用 = **同一个东西**——一个本地核心服务，三个入口：

| 入口 | 用途 | 协议 |
|---|---|---|
| CLI | 脚本 / 终端漫游 / 测试 | 子命令 |
| Web UI | 可视化节点簇 / 拖拽调权重 | REST / JSON |
| AI | 后续暴露给 agent | 可选 MCP server |

**技术栈：Go 核心 + Python 语义层（可选）**

| 组件 | 归谁 | 理由 |
|---|---|---|
| 双链解析 / 图引擎 / 边权存储 | Go | 纯文本 + 图遍历，标准库够用 |
| 四维打分 / 反馈闭环 | Go | 纯算术，无 AI |
| CLI / REST JSON API | Go | net/http 零框架 |
| 可选 MCP server | Go | dsh 生态现成的 AI 桥 |
| embedding / 语义锚定 | Python | AI 生态最强，本地模型现成 |
| 补链建议 / 推荐理由 | Python | LLM 调用最顺手 |

**存储：SQLite 主存储（默认），JSON 仅导出（2026-08-21 修订）**

规模账决定存储选型，不是"JSON 够用"一句话能盖住的：

| 场景 | 节点数 | JSON 全量写问题 |
|---|---|---|
| Obsidian 文件级 | 几百 | 可接受 |
| 虎鲸块级 | **几千~上万** | 每次 touch 重写 5-20MB，写放大明显 |
| 卡片盒重度用户 | **数万~十几万** | 彻底不可行 |

- **运行时不变**：内存邻接表（数万节点 ~ 百 MB 级，加载毫秒级），SQLite 只解决**持久化写路径**
- **SQLite 是嵌入式库不是服务器**：用 `modernc.org/sqlite`（纯 Go，零 CGO），交叉编译三平台无障碍，契合 §6.10 跨平台设计
- 收益：增量写（WAL 单行 UPDATE，热启动转移计数的高频小写场景天然适配）/ 事务（多进程不打架）/ SQL 查询（过滤统计）/ 崩溃恢复
- **不做双后端**：默认 SQLite 一个存储后端覆盖所有规模；JSON 降级为导出 / 备份 / 调试格式（`seren export`）
- 规模边界：百万级节点才需要图数据库——那是 §6.9 边界声明的领域，个人工具不碰

**多库：每库一 DB，内存层可合并（2026-08-21 补充）**

- 每个笔记软件实例（Obsidian vault / 虎鲸库）= 一个 adapter = 一个 SQLite 文件，放在库内 `.serendipity/db-<库路径 hash>.sqlite`
- **便携闭环〔修订 #12〕**：库**手动迁移/拷贝**时图跟着走（库在哪，图就在哪）。但 `.serendipity/` **不进云同步**，走 Obsidian Sync / iCloud 时只有**结构可重建**（双链在源文件里），**行为层（边权 / heat / 转移计数）本地化**、不跨机跟随。这是刻意取舍——台式机的阅读习惯不该影响笔记本；如需跨机同步行为，另设导出/导入。
- **跨库漫游 = 高阶功能，后置**：发生在内存层（同时加载多个 DB 合并成内存图），存储层保持隔离——未来支持不需要存储重构
- 同名库用库路径 hash 区分，改名 / 移动后自动识别

**启动对账（冷同步，日常高频路径，2026-08-21 补充）**

内核离线期间笔记被增删改 → 文件监听不可用 → 启动时必须主动扫描比对（纯增量不成立：Obsidian / 虎鲸均无可靠的离线变更日志）。

```
启动 → 快速扫描 vault（路径 + mtime + 大小，不做内容解析）
     → 与 DB 逐条对账：
        ① DB 有、磁盘无 → 软删除（valid_until 标记，边权保留）
        ② 磁盘有、DB 无 → 解析建节点
        ③ 两边有但 mtime 变 → 重解析内容，更新文本 / 双链 / 标签
     → 对账完成 → 开始文件监听（此后走实时增量）
```

- **快慢分离**：元数据遍历（数万文件 ~ 秒级）vs 内容重解析（只发生变更的文件）
- **软删除 = bi-temporal**（mneme §5.7 同款）：文件没了不代表关系没了——搬走 / 换库时边权不丢，未来找回 / 跨库合并可用
- **`.serendipity/` 必须排除在对账范围外**——防 DB 文件自触发变更检测死循环
- 虎鲸块 ID 稳定（数字 ID，改名 / 移动不漂移）；**Obsidian 文件名即 ID，改名会被判为"删一个 + 加一个"——〔修订 #8〕v1 必做改名迁移**：按**内容哈希 / 路径相似度**识别改名，把旧节点的边权 / 转移计数**合并迁移**到新节点，避免高频改名孤儿化行为数据。软删除保留边权是"找回兜底"，改名迁移是"无缝续接"，二者并存。
- **最终一致性**：mtime 极端漏报由"用户下次再改该文件"兜底收敛，无需内容哈希（对账用）；内容哈希只用于改名识别，二者用途不同。
- 与 §6.7 的关系：实时监听 = 热同步，启动对账 = 冷同步，**共用同一套解析器**——对账不是新系统，只是给"同步"补上离线区间

**〔v0.1.2 落地〕`seren refresh` + Web `/api/refresh`（对账刷新 v1）**：使用者增删改笔记后手动触发，全量重解析 + 与上次持久化状态 diff（`internal/sync`，按 ID 对齐、规范化比较 Title/Type/Path/Tags/Aliases/Text/Refs 字段），报告 新增/更新/删除 明细并写回存储（幂等全量重写）。边际情况实测（TestOrca 21976 块大库）：

| 场景 | 实测行为 |
|---|---|
| 首次刷新（无存储） | 全部 added（等价 index） |
| 新增页面/块（虎鲸 CLI create_page/insert_markdown） | 新增 1 文档（段落折叠进页面） |
| 删除块（delete_blocks） | deleted；被删块的后代变链顶 → added |
| 修改文本/标题 | updated，字段级明细（title/text/aliases/refs…） |
| 引用增删 | updated 的 refs 字段 + 引用±N；同文档内引用正确丢弃 |
| 块移动页面（归属变化） | 两个文档都 updated |
| 删除被引用块（悬空） | deleted + 引用方 updated(refs -1) |
| 重复刷新 | 幂等（全 unchanged） |
| 虎鲸 app 独占锁活库 | 文件拷贝快照 + WAL recovery + integrity_check 兜底（VACUUM INTO 拿不到读锁时），实测 0.84s |

**对账正确性的三个前提（v0.1.2 实测确认）**：① 快照必须含未 checkpoint 的 WAL（VACUUM INTO 优先；文件拷贝路径先 wal 后 db + 打开时自动 recovery）；② 虎鲸 schema 的生成列 `name_p = to_pinyin(name)` 需确定性函数 stub（否则 VACUUM INTO 报 malformed）；③ Tags/Aliases/Refs 比较前排序（adapter 输出顺序不稳定会误报）。自动监听（fsnotify / DB 轮询）是 v1.5 的热同步，不在 v1。

**〔v0.1.4 落地〕自动监听 + 反馈埋点 + 虎鲸跳转（克制设计，用户拍板"不要太频繁"）**：

- **自动监听（internal/watch）**：轮询式（非事件监听，频率完全可控）——Obsidian 逐 .md 文件比对 (mtime,size) 快照（含新增/删除），虎鲸 stat 库文件。检测到变化进入"待刷新"，**刷新节流 60s 合并窗口**（连续编辑吸收为至多每分钟一次全量刷新）。**排除 `.serendipity/.git/.obsidian/.trash/.dsh`**——store 写入自身产物不自触发"变化→刷新→写入→再变化"无限循环（正反馈核心防线）。刷新失败仅记日志、保留待刷新，节流后重试，不轰炸。serve 默认开启，`--watch-off` 关闭，`--watch-interval`（轮询秒）/`--watch-throttle`（节流秒）可调。
- **反馈埋点（POST /api/touch）**：Web 端点击节点上报 {target, from} → store 独立 touch 表（**Save 全量重写不清除**，容量上限 5000 条防无限增长）。**v1 不做边权演化**——埋点只记录不演化，"点击→边权变→结果变→再点击"的跑飞在源头切断；将来要看数据再决定演化策略。
- **虎鲸跳转（orca-note://）**：卡片「打开」生成 `orca-note://<repo>/block?blockId=<id>`（协议见 orcanote-agent-skills），repo 名 = `--repo` 或库文件名（去 .db）。
- **Web 可见性**：自动刷新后 revision+1，前端每 30s 轮询 stats 对比，提示"库已自动更新"。

**查询降级策略（〔修订 #10〕新增）**：个人 vault 大量孤儿节点、小组件、随手链，激活扩散在稀疏/破碎图上会频繁返回空或平凡结果。v1 起内置降级——当查询点无/少链接时，回退到**标签命中 + 全文 LIKE** 兜底，保证每次查询都有输出；补链（AI）是 v2 的正规解法。**〔实测〕已在真实库确认**（示例库细节已脱敏，见 `docs/spike-report.md`）：存在大量孤儿节点、正文页零链接、图高度集中于索引子图——降级策略是刚需不是保险。

**配置分层（2026-08-21 补充）**

全系统约 20 项配置，三层冰山模型——只把层 1 暴露给用户：

| 层 | 内容 | 数量 | 暴露策略 |
|---|---|---|---|
| 层 1 用户配置 | adapter 路径列表、Web / MCP / 语义层开关、人工旋钮（兴趣 / 难度）、输出规模、HTTP 端口、场景预设 | ~8-10 项（全带默认） | 用户可见 |
| 层 2 算法参数 | λ / θ / maxHops、热启动（停留 / 回跳 / 置信 / EWMA）、边初始权重、四维权重 αβγδ | ~12 项 | 内置默认，高级用户改配置覆盖 |
| 层 3 运行时状态 | heat、转移计数、边权 | — | 在 DB 内，不是配置 |

**〔修订 #13〕四维权重 αβγδ v1 只有一组全局默认**，场景预设（导航/复习/漂移切换）是 v2 的可选项，不做进 v1。载体三级优先级：vault 级 `config.yaml`（跟库走）> 全局 config（`~/.serendipity/`，端口 / 凭据）> 内置默认。非法值回退默认（延续 mneme 防御性校验风格）。

**配置格式决策**：**配置用 YAML，数据用 JSON**——YAML 可注释（配置自文档化，层 2 参数暴露给高级用户时注释即说明书）、人读人写友好；yaml.v3（纯 Go 零 CGO）实现 YAML 1.2，`on/yes/时间` 类型陷阱基本消除，不破坏跨平台单二进制。JSON 保留给机器读写场景：导出 / 备份 / REST API / 运行时状态（零依赖 + 无歧义 + 与 API 同构）。

**关键约束：Python 是可选项**——没有 Python 环境，纯图漫游功能必须完整可用（Go 单二进制）；检测到语义层在线，embedding / 补链 / 理由自动启用。两套运行时的复杂度靠"进程隔离 + localhost HTTP 通信 + 可选"关在笼子里：语义层崩了，核心照跑。

Go 当核心的理由：单文件分发、秒启动、交叉编译（Windows 开发 / Linux 部署）；网络环境差时"装个 Python 再跑"是劝退，单二进制是硬需求。Python 语义层的理由：本地 embedding 推理生态最强（onnxruntime 等），且 v1 纯图阶段根本不碰它。

**AI 通道用 MCP 而非自定义 REST**：MCP 是 agent 消费本地能力的通用协议，任何 AI 客户端（含 dsh-mneme 类 agent）接上即用。REST 给 Web / CLI 自用，MCP 给 AI 用，同一个核心。

**落地顺序（〔修订 #11〕）：**

- **v1（纯 Go）**：解析 + 图引擎 + 边权 + 四维打分 + CLI + REST——**先 Obsidian-only**，验证 serendipity
- **v1.5（纯 Go）**：虎鲸 adapter（SQLite 直读 + 拷贝；格式已解码见 §6.9.1，去风险项 = 监听/对账改 DB 轮询）
- **v2（插 Python）**：语义锚定 + 补链 + 推荐理由
- **v3（可选）**：MCP server 暴露给 AI

v1 已能回答"图谱漫游有没有增量价值"这个核心问题，Python 层不影响 v1 验证。

### 6.9 多笔记软件适配：统一图格式 + adapter

**策略**：Go 核心只认识一种**统一图格式**（节点 + 边 + 标签），每个笔记软件一个 adapter 负责把自己的数据转成这个格式。核心零感知，适配器可插拔——这是现在唯一必须预留的工程抽象。

**内核职责边界：Document API = 我们的 VFS（2026-08-21 补充）**

内核与 adapter 的边界（Linux VFS 哲学）：

- **事件捕获在内核**：文件监听（fsnotify，纯 OS 能力）、启动对账、图引擎、打分——全部作用在统一抽象上，不感知任何格式
- **Document API = VFS 接口**：`id · 内容 · mtime · 路径`——内核唯一的格式抽象
- **事件解释在 adapter**：路径 → 节点 ID、文件内容 → 双链 / 标签——只有 adapter 知道格式（Obsidian 文件名即 ID / 虎鲸块 ID / 思源混合）
- **adapter = 无状态纯解析器**（`parse(doc) → 节点/边/标签`、`identify(path) → id`）：不持有监听 / DB / 状态，内核包揽生命周期，adapter 只做"格式翻译"——适配工作量全在解析格式，不在系统集成
- **依赖倒置**：内核定义抽象、adapter 实现抽象，内核通过接口消费、不知实现细节
- **扩展性结论（用户拍板）**：适配更多格式 = 第三层加一个 adapter——内核、Document API、存储、图引擎全不动。未来非文件系统数据源（日历 / 邮件，见边界声明）是 Document API 接口的新实现，同样不改内核

**Document API 定稿：图自洽性 + title 与 ID 分离（2026-08-21）**

**〔实测新增〕VaultProfile：解析规则抽离（2026-08-21）**——通用 Obsidian 语法（`[[...]]`、frontmatter 块、H1）是四海皆准的，由代码固定；但"语义映射规则"（title 键优先级、别名/标签键、排除目录、类型推断）因人而异——示例库用 `name`/`*_name` 类键而非 `title`，类型按目录/文件名前缀约定推断（如 `人物_` 前缀 → 人物），这些是**库专属约定**，必须抽成可配置层，否则换库就要改 Go 代码。方案：

| 层 | 内容 | 形式 |
|---|---|---|
| 通用语法 | `[[...]]` 链接、标准 Markdown 链接（OKF）、frontmatter 块、H1 提取 | 代码固定 |
| **VaultProfile** | title_keys / alias_keys / tag_keys / excluded_dirs / 类型推断规则（目录/键/前缀/后缀）/ type_field / description_keys / resource_keys / structural_types | **YAML 画像**，内置默认 + 按库覆盖 |
| 适配器 | 非 Obsidian 软件（虎鲸等） | 独立 adapter（§6.9） |

- **画像载体**：`<vault>/.serendipity/profile.yaml` 跟库走（§6.8 配置分层收口）；缺失字段用通用默认补齐（防御性校验）。
- **新库 onboarding**：`seren profile-detect <vault>` 自动产出画像骨架（frontmatter 键普查 / 目录结构 / 文件名前缀统计 / 结构类型猜测），人工微调类型名后保存——机器产出骨架，人定语义。
- **类型字段（spike F4 落地）**：Document 增加 `Type`，实体查询默认从节点簇排除 `structural_types`（章节/大纲/报告/画布/索引/状态等机器与结构节点）——实测后输出全为内容类型（人物/线索/设定/ADR），2-hop 惊喜保留、噪音消失。
- **OKF 通用格式落地（〔v0.1.1〕Google Open Knowledge Format）**：OKF v0.1 = "一目录 markdown + YAML frontmatter" 的可移植知识格式，frontmatter 只约定六个可查询字段 `type / title / description / resource / tags / timestamp`，概念间用**普通 markdown 链接**连成图（`index.md` / `log.md` 为保留文件名）。默认解析因此内置：① 标准 markdown 链接（目标须 `.md`）与 `[[...]]` 一样入图——通用语法层直接支持；② `type_field="type"`——frontmatter 的 `type` 值即节点类型；③ `description_keys` / `resource_keys`——描述与资源地址并入正文，全文检索可命中结构化元数据；④ `--profile-name okf` 与 default-obsidian 等价。`index` / `log` **不默认结构类型化**（真实库里可能是正文页面，是否排除由各库画像 `structural_types` 自定）。参考：https://cloud.google.com/blog/products/data-analytics/how-the-open-knowledge-format-can-improve-data-sharing

**图自洽性原则（用户拍板）**：节点粒度 = 原生链接粒度——Obsidian 链接目标是页面 → 节点 = 页面；虎鲸链接目标是块 → 节点 = 块；思源（预留）同理。强行跨原生粒度（如把 Obsidian 页面拆成块节点）会产生用户看不懂的碎片图——**图的样子必须和笔记软件里的样子一致**。

**〔v0.1.1 实测修订〕虎鲸节点粒度收敛到页面**：虎鲸的"块"分页面块与内容块（页面块里装很多内容块，每段一个块），而链接目标虽为块 ID，绝大多数指向**页面块**。初版"每块一节点"把 1042 个空页面块也做成节点，标题兜底成 `块#N`，输出一片纯数字。修订：图节点 = 页面（在 app 里用户看到的就是页面），页面内内容块按 `left` 顺序链拼进页面全文，块级引用归一化到所属页面 → 页面间无向边；嵌套页面保留独立文档 + 包含边；游离内容块（快速记录）独立成文档。节点数 4919 → 1832，枢纽全为真实标题。细节见 §6.9.1。

```
Document（= 图节点，粒度 = 原生链接目标）：
  id        # 身份（Obsidian 文件名 / 虎鲸块 ID——图结构与对账用）
  title     # 语义名（锚定与展示用，见提取规则）
  path, mtime, size   # 对账（§6.8 启动对账的匹配键）
  refs      # 双链 → 其他 Document id
  tags
  fragments # 内容层（embedding / 语义检索用，不产生图节点）
```

**title 与 ID 分离（纯编号文件名的解法，示例场景：编号文件名）**：Obsidian 文件名同时承担"身份 + 语义标签"两个角色，编号文件名把二者撕裂——ID 还在（图结构无碍），语义标签没了（锚定 / 展示失效）。解法：**title 独立提取，ID 不动**。

- 提取优先级：frontmatter title > 正文第一个 H1 > 文件名兜底
- **锚定层多通道**（§3.1 升级）：文件名 + title + 标签 + 全文 LIKE（v1）→ Fragment 向量（v2）——纯编号文件名不阻塞锚定（搜"姓名"命中纯编号页面）
- **展示层用 title**：图节点显示语义名，不点开也知道是谁
- 附带收益：内容标题更新走 mtime 重解析，不误判"删 + 加"（缓解改名识别坑——注意 ID 仍以文件名计，真改名靠 §6.8 的改名迁移识别）
- 虎鲸天然有 title：别名块的别名即 title

**Fragment 内容层（不参与图结构，解决"数万字页面喂不进 embedding"）**：

- **v1 纯图不碰 embedding**：数万字页面在 v1 只是节点 ID + 边，此问题仅存在于 v2 语义层
- 图结构层 = Document（原生粒度）；内容表示层 = Fragment 化，三条用途：
  1. 页面向量 = **加权聚合**（mean pooling 按结构加权，标题段权重高）→ 候选预筛（粗）
  2. **Fragment 向量索引** → 语义锚定精筛（命中页内某段 → 定位到页面节点，主路径）
  3. **LLM 摘要**（可选增强）→ 补链 / 推荐理由的上下文
- 切分策略（adapter 职责）：按结构切（标题 / 章节）优先——语义完整；无结构按段落 / ~500 字滑动窗口（重叠 50 字）；虎鲸块即最小单元不切

**适配优先级（用户拍板：自用优先）〔修订 #11〕**：当前自用 Obsidian + 虎鲸，思源不做（用户不用，Roaming 的思源身份不影响本设计）。**v1 先 Obsidian-only**（文件解析最便宜、零未知格式），虎鲸后置 v1.5。

| 软件 | 适配方式 | 特殊性 | 优先级 |
|---|---|---|---|
| Obsidian | 文件解析（最便宜） | `[[文件名]]` 语义直接，读 markdown 即得 | **v1 唯一** |
| 虎鲸（Orca Note） | **〔实测〕SQLite 直读（先拷贝再读）+ 插件导出兜底** | 块级节点 + 数字 BlockID + 三种引用（格式已解码，见 §6.9.1） | **v1.5** |
| 思源 | 预留（社区/第三方可适配） | 文件 + 块混合模型 | 不做（预留扩展点） |

**统一图格式的两个抽象（接口设计必须预留）**：

1. **节点可以是块**（有父级、可聚合到页面）——虎鲸的块、Obsidian 的无（文件即节点，天然满足）
2. **标签可以是节点**（有属性、可被引用、可当锚点）——虎鲸的别名块、Obsidian 的 tag 都建模成标签节点

这两个抽象不是为虎鲸白做：Obsidian 的 tag 同样受益（标签成为图节点后，锚定层可以直接锚在标签上）。

**虎鲸 adapter 要点**（块级带来的四项额外工作）：

| 工作项 | 说明 | 成本 |
|---|---|---|
| 块 ID → 内容映射 | `[[12345]]` 无文件名语义，需解析 ID 对应块文本 / 所属页面 | **〔实测〕低**——`Block.content` 为 JSON 分段，`"r"` 段直接内嵌目标块 ID（§6.9.1） |
| 层级边接入 | 包含关系（父块-子块）→ 依赖分增强（部分-整体 = 该先读） | 低（算法复用） |
| 输出聚合 | 块级漫游结果带"所属页面 / 父链"上下文，防碎块 | 低 |
| 标签实体节点 | `#` 别名块 = 现成实体锚，锚定层几乎免费 | 低（反而省事） |

**虎鲸格式实测（〔实测〕2026-08-21，真实虎鲸库解码，内容已脱敏；〔v0.1.1〕页面/内容块模型细化）**：

虎鲸**没有笔记文件**——数据全在库根 `OrcaNote.db`（SQLite，WAL 模式，另有日期备份）。adapter 必须改走 **SQLite 直读**而非文件解析：

| 表 | 内容 | 对图的贡献 |
|---|---|---|
| Block | `id, content(JSON), text, created, modified, parent, left` | 节点；**`content IS NULL` 的块 = 页面块**（一个页面 = 一个文档，可嵌套）；其余为**内容块**（一段 = 一个块，从属于页面）；`parent`/`left` 构成层级与顺序（`left` = 前兄弟指针） |
| BlockRef | `id, f, t, type, alias` | 边；三种 type 实测：1=正文内嵌引用、2=带别名/属性的引用、3=无别名关联引用；`alias` 列是引用标签（如 `书籍`） |
| BlockAlias | `name, block, pos` | title（块可多别名，如 `历史` + `History`）——别名即 title，锚定层直接用 |
| BlockRefData | `id, name, value` | 引用级属性（如 `状态=已读`）——v2 可作打分信号 |
| BlockProperty | `block, name, type, value` | 块级属性（含 journal 日期等） |
| BlockFTS | FTS 索引 | 全文检索现成——v1 降级策略直接可用 |

- **页面块 vs 内容块（〔v0.1.1〕用户确认的模型）**：一个页面块里会有很多内容块（每段一个块）。`text` 列是**已解析纯文本**——内联引用已渲染成 `[目标标题]`（如 `阅读了[十一个时区之旅]和[文化、权力与国家…]`），adapter 直接使用，无需再解 `content` JSON。
- **〔v0.1.1〕聚合策略**：图节点 = 页面块（type=doc）。页面自身 text + 页面内全部内容块按 `left` 链顺序拼接 → 页面全文；所有 `BlockRef` 的 f/t 先映射到"所属页面"（内容块向上找最近页面祖先），边 = 页面间无向边，映射后自环丢弃；嵌套页面（`content NULL` 且 `parent` 非空）仍是独立文档并向宿主页面加包含边；游离内容块（`parent` 为 NULL）独立成文档（type=block）。标题兜底：别名 > 页面文本首行（去行尾 ` #标签`）> 首个内容块文本首行 > `页面#N`/`块#N`。实测 4919 节点 → 1832（1042 页面 + 790 游离块），枢纽全为真实标题，漫游结果带真实书名/主题。
- **内容格式**：`Block.content` 是 JSON 分段数组——`{"t":"t","v":"文本"}` 文本段、`{"t":"r","v":目标块ID}` 引用段。**引用关系内嵌在内容里，连 markdown 解析都不需要**——"块 ID → 内容映射"从"中"降为"低"（v0.1.1 起聚合到页面后连 content JSON 都不必解，text 列已解析）。
- **读取纪律**：活库带 WAL、可能被占用——**先拷贝到 `.serendipity/` 再读，绝不锁活库**；对账基于 DB 而非文件监听（v1.5 细节）。
- **安全红线〔实测〕：`Repo` 表含用户凭据**（实测有 DeepSeek API key / 对象存储密钥）——adapter 与 `.serendipity/` 拷贝**必须排除 Repo 表**，图数据只从 Block/BlockRef/BlockAlias/BlockProperty 派生。

**为什么虎鲸可能是最顺的载体**：它的三种引用关系恰好对应四维打分的数据源——`@` 引用 → 结构 / 激活边，`#` 标签 → 锚定层，包含关系 → 依赖分。不需要新机制，现有打分直接吃。

**边界声明：数据源即 adapter，但当前只做笔记（群友讨论补充）**

群友提议"把其他软件也作为 service"（访问 journal 日记 → 关联日历今日日程 → 邮件 → 某本书）——概念上完全可行，且**架构天然支持**：adapter 模式不限定"笔记软件"，日历 / 邮件 / 书库都是同一个 adapter 接口的实例。**泛化 = 增加 adapter 类型，不是新架构。**

**"不是语义引擎通读"的洞察**（群友）：结构化数据源（日历事件 / 邮件元数据 / 文件路径）直接以精确名 + 属性成节点和边，**零语义引擎**；只有内容型数据源（笔记正文、书摘）才需要 embedding / TF-IDF。**反直觉推论：泛化到万物后，语义层占比反而变小**——泛化不增加 AI 依赖，反而稀释它。

**为什么不做现在**（历史教训 + 现实成本）：

- 语义桌面愿景（KDE Nepomuk / 微软 WinFS）失败的根因 = **adapter 维护量随数据源线性增长** + "关联了然后呢"的用户价值不明确
- 日历 / 邮件要接 API / 认证 / 增量同步 / 隐私边界——另一个量级的工程
- **内核语言无需因此升级**：个人规模 Go 性能过剩；"可移植内核"是架构属性（三入口 + 统一图格式已兑现），不是换 Rust / Zig 的理由——若未来真开源内核给第三方，再独立评估重写

**结论**：adapter 接口**不锁死数据源类型**（预留扩展点），落地范围**钉死在笔记**（Obsidian + 虎鲸）。

### 6.10 跨平台与便携性

目标：Win / Linux / Mac 三平台。按层评估：

| 层 | 跨平台难度 | 说明 |
|---|---|---|
| Go 核心 | 低 | 交叉编译（GOOS/GOARCH）三平台一行命令，单二进制 |
| Web UI | 中低 | 浏览器 / WebView 三平台都有；壳方案二选一（见下） |
| 文件系统交互 | 中 | 三个纪律（见下） |
| Python 语义层（v2） | 高 | 模型 + 运行时三平台分别打包，v2 再处理，不阻塞 |

**Web 壳方案**：

| 方案 | 体验 | 成本 | 选择 |
|---|---|---|---|
| CLI + localhost（Go 起 HTTP，浏览器打开） | 能用不好用 | 零 | **v1** |
| Wails（Go 生态 WebView 壳） | 原生窗口、单可执行文件 | 中（Linux 需 WebKitGTK） | **v2 按需** |

不用 Electron（三平台各 ~100MB）；要原生壳用 Wails——与 Go 核心同语言，不引第二运行时。

**三个文件系统纪律（v1 就要守）**：

1. **路径规范化**：Windows 大小写不敏感 vs macOS/Linux 敏感——双链文件名匹配统一小写归一，否则同篇笔记跨平台"链上/链不上"不一致
2. **换行符归一**：CRLF（Windows）vs LF（Unix）——解析与索引前统一，否则同样内容两个平台算两个节点
3. **文件监听节流**：fsnotify 三平台可用，但 Windows 大量小文件会事件风暴——增量同步必须合并/节流

**便携性设计**：SQLite 库内**存相对路径**，配置只存 vault 根——笔记库在 Windows ↔ Mac 之间**手动拷贝**（换机器）图不烂（结构层）。这是最容易被忽略、最伤人的跨平台细节。〔修订 #12〕行为层不随手动拷贝之外的方式迁移。

### 6.11 语义层模型选型（v2）

语义层涉及**两类不同的模型**，配置成本完全不同，必须分开说：

| | 向量化模型（Embedding） | 通用模型（LLM） |
|---|---|---|
| 输入 → 输出 | 文本 → 向量 | 文本 → 文本（生成） |
| 用途 | 语义锚定、候选预筛 | 补链建议、推荐理由 |
| 引擎 | onnxruntime / FastEmbed | ollama / OpenAI 兼容 API |
| 重量 | 轻（100MB~1GB） | 重（本地几 GB 起） |

**推理引擎**：onnxruntime 本身零配置（pip install 即用）。但裸用只是引擎——**模型文件 + tokenizer 要自己配**，中文分词自接易踩坑。用 **FastEmbed**（Qdrant 家）封装：pip install 一行，模型自动下载缓存、自带分词、无 torch 依赖——这是"泛用性"的第一个答案。

**中文硬约束**：笔记以中文为主，英文模型（如 all-MiniLM）效果差——选 `bge-small-zh`（~100MB）起步，不够再上更大的。

**泛用性来自协议，不是特定软件**：语义层做成 **OpenAI 兼容 API 客户端**（薄适配器：配置 base_url + model 名），后端可插拔——

| 后端 | 场景 | 说明 |
|---|---|---|
| FastEmbed | 最轻，纯 embedding | 本地直连，无服务 |
| ollama | 本地统一服务 | embedding + LLM 一个服务，OpenAI 兼容 |
| 云端 API（DeepSeek / 通义等） | 有网时 | 同一协议，改配置即切 |

**推荐组合**：v2 默认 FastEmbed 做 embedding（起步阶段纯锚定不需要 LLM）；补链 / 推荐理由按需接 ollama（本地）或云端 API。切换零代码改动。

## 七、诚实的评估

### 7.1 值钱的场景

1. **embedding 桥不动的长尾关系**：语义不相似但关系明确（跨项目工具偏好、项目换方案的失效）——激活扩散能桥，TF-IDF/向量未必
2. **可解释 / 可干预的导航**：用户想"知道为什么"或"主动改一下"——黑盒推荐做不到
3. **探索性发现（serendipity）**：漫游特有的价值——"我没想到但确实相关"的惊喜节点，检索和调度都不测这个

### 7.2 三个难点

1. **反馈信号弱**（见 §6.3）——无可靠反馈，权重演化和推荐质量都悬空
2. **"程序化经验"不是推荐器能交付的**：阅读导航建立的是陈述性知识（知道什么）；程序性知识（会做什么）需要练习。图谱能做到的最大贡献是**按依赖顺序披露**（先读前置再读衍生）
3. **heat 不引入核心路径（γ 默认 0）**：mneme 必须 heat 的三个理由——自动积累需清理、兴趣漂移快、注入预算极稀缺——在笔记场景**全部不成立**：笔记是用户精选（无需自动降级）、查询驱动（意图由查询表达，激活分已承担"离当前意图多近"）、节点簇输出预算宽松。三个用途逐个检查：**排序偏移**冗余于激活分；**降级/归档**不该作用于用户主动保存的知识；**边权衰减**会让旧知识被压死（历史关系不会过时）。保留两个**可选扩展点**：① 锚定消歧（模糊查询多命中时，选最近活跃的锚点）② 漂移检测（未来做主题切换提醒）。复习提醒不靠 heat——那是 SRS 的职责（§7.3 分立立场）。

### 7.3 开放问题

1. ~~载体~~ **已决**：本地 CLI + Web（§6.8），不绑死任何笔记软件；插件只作未来的可选分发形态。剩余问题：Web UI 形态（本地静态页 + REST，还是内嵌服务端渲染）
2. "读"的反馈信号：接受弱信号还是强制显式标记？
3. 与现有 SRS（Anki 等）的关系：**分立**（本文只管拓扑驱动的导航，复习交给现有工具）——推荐立场，除非用户有相反证据
4. ~~α/β/γ/δ 四维权重是否需要场景级配置~~ **已决（〔修订 #13〕）**：v1 只有一组全局默认，场景级配置后置 v2。

## 八、验证实验（MVP）

参照系已变：Roaming 已证明"推荐器有没有用"，本文要验证的只剩一个干净命题：

> **"同一个激活引擎，从 entity_relations 换到笔记双链，输出给人看，能否产生'我没想到但确实相关'的节点？"**

- **数据**：个人笔记库（Obsidian，用户自用优先）解析双链成图；公开 Zettelkasten 样例库兜底
- **查询集**：10 个实际关心的主题
- **输出**：每主题 top-10 节点 + 激活路径
- **判定〔修订 #6〕：定性探索，不设数字门槛**——"serendipity（意外发现率）"是"我没想到但确实相关"的惊喜节点占比，只能用户自评、单用户 n=1 且不盲，任何"≥30%"式的硬门槛在 n=1 下都是伪严谨。改为：遍历 10 个查询，**逐条记录**惊喜节点 / 可解释性 / 干预效果，用文字结论判断方向；同场覆盖 §7.1 的三个价值点（长尾关系、可解释/可干预、serendipity），不只测惊喜率。
- **对照基线〔修订 #7〕：v1 后置**——先直接看图谱版能否产出惊喜节点；Roaming 的 TF-IDF 管道对比（相关节点召回增量）留到图谱版方向确认后再做，避免为对比额外造一套管道。
- **门槛（定性）**：图谱版稳定产出"我没想到但确实相关"的节点，且可解释/可干预两条成立 → 方向成立，投入工程化
